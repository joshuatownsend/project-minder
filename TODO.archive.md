## MCP & Config Security

*Inspired by [mcpware/cross-code-organizer](https://github.com/mcpware/cross-code-organizer), which connects to live MCP servers and runs multi-layer threat analysis. MCP servers are a growing attack surface — malicious tool descriptions can exfiltrate credentials, inject prompts, or silently change behavior between scans ("rug-pulls").*

- [x] **MCP security scanner** — Connect to each configured MCP server (from `.mcp.json` + `settings.json`) and introspect tool definitions via JSON-RPC 2.0, then run a multi-layer threat scan: (1) **Deobfuscation layer** — 8 passes before pattern matching: strip zero-width Unicode, remove bidirectional text controls, strip HTML comments, Base64-decode encoded blocks, normalize escape sequences, detect leetspeak substitutions; (2) **Pattern layer** — 60+ regex rules across threat categories: prompt injection, tool poisoning, credential harvesting (flag parameter names like `webhook_url`, `ssh_key`, `api_token`), data exfiltration, code execution triggers, sensitive file access, persistence mechanisms; (3) **Hash layer** — SHA256-fingerprint each tool description at first scan; alert when a definition changes unexpectedly on re-scan ("rug-pull" detection). Safety guards: 15-second timeout per server, 500-tool cap, 50KB description limit, 5 concurrent connections, stdio + HTTP/SSE transport. Surface findings in the Config browser's MCP section as a "Security" tab: severity badges (critical / high / medium / low), deobfuscated preview, rug-pull diff, last-scanned timestamp. Hash baselines persisted to `.minder.json` or a SQLite table. New module: `src/lib/scanner/mcpSecurityScanner.ts`. Ref: `src/security-scanner.mjs` + 8-pass deobfuscation + 60+ patterns + SHA256 rug-pull in `mcpware/cross-code-organizer`.

- [x] **Task queue & cron scheduler** — A task queue for composing and dispatching work to Claude Code directly from the dashboard. A background dispatcher (Node.js child process spawned by the Next.js server, or a dedicated `src/lib/dispatcher.ts` loop running as a `globalThis` singleton) picks up `status='pending'` tasks, honors `requires_approval` → `awaiting_approval` promotion, and spawns `claude` CLI as a child process. Ref: `DECISION:` + `INBOX:` parsing (fence-aware, skips triple-backtick blocks) + stdin injection + partial UNIQUE index in `build-your-own-dashboard-prompt.md`.
- [x] **Emergency stop (kill-switch for dispatched agents)** — A red "Emergency Stop" button prominently placed on the dashboard that, when confirmed, SIGTERMs only the Claude Code child processes that were spawned by the Project Minder dispatcher — leaving any Claude Code sessions the user started manually in their terminal unaffected. - [x] **Follow-up — Settings UI for coverage + backfill** — completed 2026-08-02. `src/components/settings/SemanticSearchSection.tsx` + a new `Semantic Search` section in `SettingsPage`, with the loop-continuation policy and all display math extracted to the dependency-free `src/lib/embeddings/progress.ts` (28 tests). *Prior art: [`simonw/claude-code-transcripts`](https://github.com/simonw/claude-code-transcripts) (Apache-2.0, Python). **Do not vendor** — ~90% of it is a JSONL→HTML renderer that Minder already beats (`adapters/claude.ts` + DB ingest + FTS5 + `/sessions`). - [x] **Spike — do the endpoints still work?** ~60 lines, scratchpad only, outside the repo. Read org UUID from `~/.claude.json`, take a token, call `/v1/sessions`, dump the response shape. Gates everything below: if #77 means the endpoints are dead for everyone, the design is moot for an hour's cost. If they work, the spike's real output is **the response schema** — `session_ingress` almost certainly does not return the local JSONL shape, and that mapping layer is the actual work in this feature.
- [x] **Fetcher + disk sync** — `src/lib/cloudSessions/fetcher.ts`, modeled on `githubActivityCache`: `globalThis` singleton, TTL, `available:false` sentinel with a `reason` enum, never throws, never blocks a scan. **No background poller** — volume is low and human-paced, so sync on explicit user action (a "Sync cloud sessions" button) plus opportunistically on project-detail open. Hitting an undocumented endpoint on user intent rather than on a timer keeps the failure surface small. Materialize to `~/.minder/cloud-sessions/projects/<slug>/<sessionId>.jsonl` — same on-disk layout as a real Claude home, so a broken endpoint degrades to *stale but present* rather than *gone*.
- [x] **`claude-cloud` adapter** — thin; reuses `parseSessionTurns` verbatim and tags `source: "claude-cloud"`. Deliberately **not** a network adapter: `SessionAdapter` is filesystem-shaped (`SessionFile.filePath`), and syncing to disk preserves that contract instead of widening the interface for one caller. The `source` field already threads through ingest/usage/sessions from Wave 10.2a, so classifier, cost calculator, one-shot detector, FTS5, `/costs` and the MCP tools light up with no changes.
- [x] **Attribution — strict + explicit fallback** — a cloud session has no local path, so `usageSlug`/`dev-<name>` can't help; the only join key is `owner/repo` → the scanned `remoteUrl` (reuse `parseGitHubRemote`). Attribute only on an exact match; everything else lands in an "unattributed" bucket surfaced for manual assignment, persisted in `.minder.json`. **Rejected: fuzzy name/title matching** — `/costs` is the main consumer and a mis-attributed session silently corrupts a project's number, which is worse than a missing one. Fuzzy may return later as a *suggestion* in the assignment UI only. The repo-centric use case (small fixes → PRs) should make strict matching hit high coverage anyway.
- [x] **Distribution risk — resolve before shipping to other users** — this is the blocker, not the engineering. Shipping a client for two undocumented endpoints inside a signed installer with an auto-updater means breakage lands in other people's installs and the support burden is ours. It also requires reading `~/.claude/.credentials.json`, which **violates the invariant stated in `src/lib/adapters/types.ts`** (*"Auth/credential files are never read"*) — fine as a personal choice, a changed promise when distributed. Multi-user also means token location, org UUID, and OS credential storage all vary per install (the reference tool's macOS-keychain path covers none of our Windows users). Minimum bar: **default-off feature flag** (new `FeatureFlagKey`, same discipline as `githubActivity`), explicit per-install opt-in with a consent string naming the file read and where transcripts are stored, retention/eviction policy for synced transcripts, and hard graceful degradation on endpoint change.

## 2026-08-18 — Tray lifecycle: updater/service hand-off + Foreign re-probe

- [x] **The tray updater can't replace a payload the logon service is holding (#457, Codex P2)** — `updater.rs::on_before_exit` stops the tray's *own* sidecar before exiting, because an orphan holding `resources/node/node.exe` makes the Windows installer fail on a locked file (`updater.rs:17-19`). But when the Phase A service owns the port the tray is in **attach** mode, where `observe_until_shutdown` deliberately leaves the running server alone — so if the service was installed against the app's own bundle (now possible via `--payload`), it keeps that `node.exe` locked and the update fails. On POSIX the file replacement succeeds but the service keeps serving the **old in-memory payload** until restarted, which presents as a successful update that changed nothing. Documented as a warning in `docs/help/service-mode.md` with two safe arrangements, but the real fix is a handshake: the updater should stop (and restart) a registered service it can identify — `scripts/service/lib.mjs` already has the identity-matching machinery (`buildServerIdentityMarkers` / `commandLineMatchesServer`) that would let it do so without killing an unrelated process. Needs a decision on whether the tray shells `schtasks`/`launchctl`/`systemctl` directly or calls the service CLI.
  > archived 2026-08-18 — done — the updater now stops a logon service registered against the app's own bundle, via the bundled `scripts/service.mjs` (gate + stop in `src-tauri/src/service_handoff.rs`). The open decision it recorded resolved to "call the service CLI": `schtasks /End` is structurally useless here, since Task Scheduler only ever tracked the wscript launcher that exits immediately.

- [x] **A settled `Foreign` verdict still never re-probes (residual of the cold-boot fix)** — `observe_until_shutdown` (`src-tauri/src/supervisor.rs`) sets `pending = false` once a probe comes back conclusive, and a conclusive `Foreign` is therefore permanent for the life of the tray process. If a genuinely foreign server answers on 4100, then exits, and Minder later takes the port, the 15s poll flips the status word to "running" while the note stays `port in use (foreign) — observing` — the same self-contradicting string the fix removed, in a rarer path. Deliberately left: the `Unreachable` case is the one that actually bit (it is what a booting Minder looks like), and making `Foreign` re-probe forever means polling a port we have proof isn't ours. The honest fix is probably to re-probe `Foreign` on the slow end of the backoff only, or to re-run the classification when the 15s health poll disagrees with the stored note.
  > archived 2026-08-18 — done — `observe_until_shutdown` now re-probes a `Foreign` verdict at the 60s cap, with `next_verdict`/`reprobe_interval` as pure, mutation-tested functions. Took the first of the two options the item proposed (slow re-probe) rather than cross-wiring the 15s health poll, which would have churned freshly-verified code for a smaller gain.

- [x] **Reinstall the tray + re-register the logon service so this machine actually runs the fixed build** — The cold-boot "foreign process" fix (tray-side `Foreign`/`Unreachable` split, DB `quick_check` gating) is on `main`, but **this machine boots neither binary that carries it**. The HKCU Run key was repointed to the installed `%LOCALAPPDATA%\Project Minder Tray\minder-tray.exe`, which is **v1.10.1 built 2026-08-11** — it predates the fix, so the tray half only lands after a `pnpm tray:build` + reinstall (or the next release). Separately, the `MinderDashboard` scheduled task still launches `C:\dev\project-minder\dist\minder-server\server.js` — the **dev tree**, not the installed app's bundle — so the DB half only lands once that payload is rebuilt or the task is re-registered against the app's bundle with the new `--payload` flag: `pnpm service:install --payload "$env:LOCALAPPDATA\Project Minder Tray\minder-server"`. Until both happen, a reboot will look exactly like the bug was never fixed. Verify afterwards by checking `~/.minder/logs/minder.log` for a `db: probed` line with a small `ms` value.
  > archived 2026-08-18 — obsolete — completed on 2026-08-17: v1.11.0 installed from the GitHub release, Run key repointed at it, and the `MinderDashboard` scheduled task removed rather than re-registered (the user chose "let the tray own the server").
